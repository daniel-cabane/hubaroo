# Fix: Real-Time Notifications for Kangourou Session Attempts

## 1. Objective

Reduce backend load generated by active Kangourou session attempts while keeping teacher monitoring near real time.

For Kangourou session attempts only, replace per-answer persistence and broadcasting with batched synchronization. Teachers must still see meaningful live progress, but the system must stop pushing the full attempt state on every learner input.

This is the session counterpart of feature #22. Copy that jump implementation pattern. Do not invent a third attempt-sync design.

## 2. Product Decisions Locked for This Iteration

- This feature applies only to Kangourou session attempts, not to jump attempts. Jump batching is already specified and implemented in feature #22.
- Teacher live monitoring during an active session shows progress only, not the full per-question answer state.
- The live teacher view must update these fields for each learner attempt:
	- attempt status: not started, in progress, finished;
	- remaining time;
	- number of answered questions over total questions;
	- termination reason once the attempt is finished;
	- score once available.
- During an active session, the teacher UI must not receive the full `answers` array over real-time events.
- The learner client stores only the latest answer per changed question. Intermediate edit history is out of scope.
- The batching interval defaults to 3 seconds and must be defined in one centralized constant so it can be changed later without searching through the codebase. Reuse the same 3-second value as jumps.
- Live updates continue to use the existing private `session.{id}` channel.
- On browser close, page unload, or network loss, the client makes a best-effort immediate final sync. If the request cannot reach the server, the product falls back to the existing timeout or abandon behavior. Immediate server confirmation cannot be guaranteed for hard disconnects.
- Session expiry force-termination, the 3-minute post-expiry save window, and hiding "Demander à reprendre" on expired results are feature #24. Do not implement them here. Do make the submit contract able to persist a final `answers` array so feature #24 can reuse it.

## 3. Why This Change Is Needed

The current strategy is too expensive when many learners are active at the same time. Persisting and broadcasting the full attempt, including all 26 answers, on every learner interaction creates unnecessary write volume and unnecessary event traffic.

This feature changes the contract from:

- every answer change is sent immediately;
- the teacher receives overly detailed live payloads, including the full `answers` array;

to:

- answers are buffered locally and flushed in batches;
- the teacher receives lightweight progress summaries;
- the final state is still persisted immediately when the attempt ends.

## 4. How Sessions Differ From Jumps

The implementing agent must not copy feature #22 or the jump code blindly. These differences are load-bearing:

| Topic | Jumps (feature #22) | Sessions (this feature) |
| --- | --- | --- |
| Model / answers | `JumpAttempt.question_list` with a variable length | `Attempt.answers` with a fixed 26 entries of `{ answer, status }` |
| Answer values | nullable string, max 10 | questions 0–23: `A`–`E` or `null`; questions 24–25: integer `0`–`100` or `null` |
| Status field | no per-item `status` write on sync | each change must also set `status` to `answered` or `unanswered`, using the same assignment as `updateAnswer()` |
| Auth | always authenticated; sync authorizes by `user_id` | guests are allowed; keep the current ownership rule: reject only when an authenticated user tries to mutate another authenticated user's attempt |
| Start event | already broadcasts `JumpAttemptUpdated` on create | `AttemptController::store()` currently does **not** broadcast; this feature must add an immediate start event |
| Per-answer writes | jump `updateAnswer()` no longer broadcasts | session `updateAnswer()` currently persists one answer **and broadcasts the full attempt**; this is the expensive path to replace |
| Submit body | jump submit already accepts authoritative `question_list` | session submit currently accepts only `timer` and `termination`; it must start accepting an authoritative `answers` array |
| Teacher surfaces | course/division jump observation modals, roster-based | `session-details-view` + `AttemptsTable` (attempt list, including guests) and `division-details-view` + `DivisionAttemptsTable` (class roster) |
| Identity on the row | `user_id` is always present | guests have `user_id: null`; teacher rows must keep using `attempt.id` and `name` |
| Extra time | jump payload does not need to drive a learner timer refresh from the same event | the learner `attempt-view` listens to `AttemptUpdated` on the session channel and applies `extra_time` after rejoin approval; the summary payload **must** keep `extra_time` |
| Grading | jump score is available on the attempt record | delayed correction may leave `score` null after submit until the session expires; do not invent a score |
| Session activity | jump sync does not check parent expiry the same way | current `updateAnswer()` rejects writes when the session is no longer active; keep that rule for active sync. Final submit already works on an expired session and must keep working |
| Channel audience | jump channel is class-scoped | authenticated learners with an attempt are also authorized on `session.{id}` because they need `SessionExpired`; summaries must not leak full answers to other learners |

Do not unify session and jump attempts. Feature `XX - Unify attempt.md` is out of scope.

## 6. Scope

### In Scope

- batching learner answer persistence for active Kangourou session attempts;
- immediate real-time event when a session attempt starts;
- periodic batched sync while the attempt is active;
- immediate final real-time event when the attempt finishes;
- teacher UI updates based on lightweight progress payloads;
- preserving guest attempts, delayed correction, extra time, and existing submit/grading behavior;
- making final submit persist the local `answers` array so unsynced answers are not lost;
- best-effort final sync on browser close or disconnect scenarios;
- backend and frontend tests for the new contract.

### Out of Scope

- preserving a full history of every intermediate learner answer edit;
- real-time streaming of full per-question answer content during an active session;
- redesigning Kangourou grading, delayed correction, shuffle, blur security, or question papers;
- changes to jump attempt behavior;
- implementing feature #24 session expiry force-stop, the 3-minute post-expiry save window, or results-view rejoin-button hiding;
- unifying session and jump attempts;
- introducing a new teacher-facing analytics surface;
- tightening guest ownership beyond the current authenticated-user check.

## 7. User-Visible Behavior

### 7.1 Learner Experience

When a learner starts a session attempt:

- the attempt is created immediately on the backend, including the existing guest-name and private-session membership rules;
- the existing session start behavior remains intact;
- a real-time event is broadcast immediately so authorized teachers can see that the learner has started.

While the learner is answering questions:

- the learner UI updates immediately and optimistically on the client;
- answers are stored locally in memory as pending changes;
- the client does not call the backend for every single answer change, including numeric keypad edits;
- every 3 seconds, if there are unsynced changes, the client sends one batched sync request containing the latest value for each changed question;
- if the learner changes the same answer several times inside one interval, only the final value is sent;
- clearing a previously answered question counts as a change and must be sent.

When the learner ends the attempt:

- the system performs a best-effort final sync of any unsent local changes;
- the attempt is then finalized through the existing submit flow, now carrying the authoritative local `answers` array;
- a real-time event is broadcast immediately so teachers see the finished state.

Termination paths covered by this feature:

- manual submit;
- manual quit or abandon, including confirmed route leave;
- time expiry of the learner countdown;
- blur timeout;
- `SessionExpired` auto-submit already present in `attempt-view.vue`;
- browser close or page unload, best effort only;
- network disconnect, best effort only.

Do not add a new teacher forced-stop in this feature. If a current path already finalizes the attempt, it must flush unsynced answers first.

### 7.2 Teacher Experience

There are two teacher observation surfaces, and they are not the same as jump observation.

#### Session details (`AttemptsTable`)

This is an attempt list, not a class roster:

- it includes guests and learners who are not in a linked division;
- a learner who has not started does not appear;
- the existing name filter and column sort stay;
- incoming events must merge into the existing row by `attempt.id`;
- a newly started attempt may be appended;
- live updates must not invent a hidden roster of non-starters.

#### Division session modals (`DivisionAttemptsTable`)

This is roster-based, like jump observation:

- the teacher sees the class roster immediately, including learners who have not started yet;
- the table keeps a stable student order based on the existing class-name sort and must not reorder rows on each incoming event;
- attempts appear on the matching student row as learners start;
- match rows by `attempt.user_id` for authenticated class members;
- guests are not part of this roster table.

For active session monitoring, each visible in-progress row must show at least:

- learner identity (`name`, or class name in the division table);
- status;
- remaining time;
- answered count over total questions, which is 26 for a Kangourou paper;
- last update freshness, either directly or through a clear stale-state indicator.

Recommended active-row presentation:

- a compact progress label such as `8 / 26` answers;
- an optional lightweight progress bar if it can be implemented without introducing new complexity;
- a local countdown based on the latest synced timer value;
- a subtle freshness indicator such as `updated a few seconds ago` when the data is getting stale.

The teacher does not need to see the live per-question answer chip grid while the session attempt is still in progress.

Teacher observation must support these presentation states:

- `Not started`: division roster only; learner has no attempt yet. Do not show this state in `AttemptsTable`.
- `In progress`: learner has an active attempt and recent sync data;
- `Sync delayed`: learner has an active attempt but no refresh has arrived for more than two sync intervals; this is a UI-only state and must not be persisted as a backend attempt status;
- `Finished`: learner attempt is completed.

The UI must not show disruptive feedback for normal live traffic:

- no toast for every incoming event;
- no row flash that makes the table hard to scan;
- only small, unobtrusive row-level updates.

When the attempt is finished:

- the teacher row updates to show the finished state;
- the countdown stops;
- termination is reflected correctly;
- score is shown when available, including `—` while delayed correction leaves it null;
- detailed answer chips remain accessible for finished attempts through the existing table layout, using answers from the details payload or an on-demand show fetch, never from the live event.

When the teacher needs the full answer grid:

- finished or expired review may keep the existing chip row if `answers` is already present from `fetchSessionDetails`;
- if a finished attempt arrives or is updated as a summary without `answers`, fetch the full attempt from `GET /api/attempts/{attempt}`;
- that fetch must have explicit loading, success, and error/retry states rather than rendering an empty chip row as if the learner answered nothing.

## 8. Functional Requirements

### 8.1 Start Event

On successful session attempt creation:

- persist the new attempt as today, including guest `name` and recovery `code`;
- broadcast `AttemptUpdated` immediately;
- send a lightweight summary payload only, not the full `answers` array.

### 8.2 Active Sync Behavior

During an active session attempt:

- keep the current attempt state locally in the learner client;
- maintain a dirty map keyed by immutable zero-based question index (`0`–`25`);
- sync only when the dirty map is not empty;
- send at most one active sync request at a time for a given attempt;
- if a flush is requested while another flush is in flight, coalesce the new changes and send one additional flush immediately after the current request completes;
- do not send heartbeat writes when nothing changed.

Backend sync rules:

- apply all incoming changes to `answers` in one write;
- for each change, set `answers[index].answer` and `answers[index].status` using the same logic as `updateAnswer()`;
- update `timer` when provided;
- reject unauthorized access, finished-attempt syncs, invalid indices, invalid answer values, and syncs against a session that is no longer active;
- allow guest callers, using the current ownership rule rather than requiring `Auth::id() === attempt.user_id`;
- return `204 No Content` on success;
- broadcast a live update only when the sync produced a meaningful change.

### 8.3 Finalization Behavior

For controlled endings such as submit, timeout, blur timeout, `SessionExpired` auto-submit, or explicit abandon:

- stop the periodic sync loop;
- attempt a final sync of unsent changes;
- call the submit endpoint with the authoritative final `answers` array;
- mark the attempt as finished exactly once;
- keep delayed-correction grading behavior unchanged;
- broadcast the final summary event immediately.

For uncontrolled endings such as hard disconnect:

- send a best-effort request using browser unload-safe mechanisms, including the local `answers` array;
- if the request does not reach the server, rely on the existing timeout or abandon lifecycle.

### 8.4 Teacher Event Audience

- Continue using the existing private `session.{kangourou_session_id}` channel.
- Session authors and authenticated learners who already have an attempt on that session may receive the event, because learners already use this channel for `SessionExpired` and extra-time updates.
- The payload must not include `answers`, so other learners cannot observe classmates’ full answer grids.
- A learner client must keep ignoring other learners’ events and must only apply `extra_time` when `event.attempt.id` matches the local attempt.

### 8.5 Teacher Monitoring UX Rules

- `AttemptsTable` renders from the session’s attempt list. Incoming events enrich existing rows by `id` or append a newly started attempt.
- `DivisionAttemptsTable` renders from the class roster. Incoming events enrich the matching student row rather than creating a separate live-only list.
- A class member with no attempt remains visible as `Not started` / `Aucune tentative`.
- A learner row must not disappear just because no new event arrives.
- Merge summaries into existing objects. Never replace a loaded attempt with a summary in a way that deletes `answers`, `name`, or other fields the table still needs.
- The UI may derive a `Sync delayed` state when the last event age exceeds two batching intervals, but it must never convert that presentation state into a persisted attempt status.
- Opening or rendering detailed chips for a finished attempt that lacks `answers` must fetch the authoritative full attempt payload.

## 9. Data Contract

### 9.1 Batched Sync Request

Add a dedicated active-sync endpoint for session attempts.

Recommended route:

- `PATCH /api/attempts/{attempt}/sync`

Recommended request body:

```json
{
	"timer": 421,
	"changes": [
		{ "question_index": 2, "answer": "B" },
		{ "question_index": 7, "answer": null },
		{ "question_index": 24, "answer": 17 }
	]
}
```

Request rules:

- `timer` is optional but should be sent whenever available so teacher progress can stay accurate;
- `changes` is required when a sync is sent;
- each change item must contain:
	- `question_index`: integer, zero-based, `0`–`25`;
	- `answer`: same validation envelope as `UpdateAnswerRequest` for that index (`A`–`E` or `null` for 0–23; integer `0`–`100` or `null` for 24–25).

Response rules:

- a successful active sync may return `204 No Content`;
- the learner client should not depend on the server returning a refreshed full attempt during active sync;
- invalid indices or invalid answer values must return validation errors;
- syncing a finished attempt must be rejected cleanly;
- syncing an attempt whose session is no longer active must be rejected cleanly, using the current `updateAnswer()` behavior.

### 9.2 Final Submit Request

Keep `POST /api/attempts/{attempt}/submit`.

The submit request must remain authoritative and must include the final local `answers` array so that unsent local changes are not lost if the last periodic batch has not completed yet.

This means:

- periodic sync sends deltas only;
- final submit sends the full final attempt answers.

This is intentionally simpler and safer than trying to guarantee perfect ordering for every network edge case.

Submit rules:

- accept `timer`, `termination`, and optional `answers`;
- if `answers` is present, persist it before grading;
- keep delayed-correction and immediate-correction behavior unchanged;
- keep the existing ability to submit after the session has expired;
- do not implement feature #24’s 3-minute post-expiry sync window here.

## 10. Event Contract

Reuse the existing `AttemptUpdated` event name and `session.{id}` channel.

Change the broadcast payload to a lightweight attempt summary.

Recommended payload shape:

```json
{
	"attempt": {
		"id": 123,
		"kangourou_session_id": 45,
		"user_id": 9,
		"name": "Jean DUPONT",
		"status": "inProgress",
		"termination": "none",
		"timer": 421,
		"extra_time": 0,
		"answered_count": 8,
		"total_questions": 26,
		"score": null,
		"updated_at": "2026-07-26T12:34:56Z"
	}
}
```

Payload rules:

- do not broadcast `answers` or a nested `user` object for active monitoring;
- include `name` so guest rows can appear in `AttemptsTable` without a refetch;
- include `extra_time` so the learner view can keep applying rejoin-approved time;
- include `score` when it exists; leave it `null` while delayed correction has not graded yet;
- keep `user_id`, which may be `null` for guests;
- `answered_count` is the number of entries whose `answer` is not `null`;
- `total_questions` is `count($attempt->answers)`, which is 26 for a normal Kangourou paper;
- use `updated_at` as the freshness timestamp unless the implementation introduces a dedicated field for this purpose.

### 11.2 Teacher Observation Views

The teacher observation UIs currently replace full attempt objects pushed by `AttemptUpdated`.

They must be updated to merge summary payloads instead.

Required changes:

- keep `AttemptsTable` filter/sort behavior, and merge by `attempt.id`;
- keep `DivisionAttemptsTable` student order stable while rows update;
- render `Not started` only in the division table;
- render `In progress`, `Sync delayed`, and `Finished` presentation states clearly;
- show last-update freshness when useful, especially for `Sync delayed` rows;
- keep score display for finished states, including delayed-correction `null`;
- when a teacher needs answer chips for a finished attempt that has no `answers` in memory, fetch the full attempt on demand using the existing show endpoint;
- add explicit loading and retry behavior for that detail fetch.

### 11.3 Teacher Observation Interaction Rules

- Clicking a learner row must remain lightweight and predictable; do not force a full session or division reload.
- The observation view must remain usable if one learner detail fetch fails.
- If the session expires while the observation view is open, keep the current expiry UX. Do not implement feature #24’s force-terminate-and-redirect behavior here.
- Live updates must patch the relevant row only; avoid refetching the entire session details payload on every `AttemptUpdated` event.

### 11.4 Teacher Timer Display

Do not generate extra backend traffic only to animate a countdown.

Instead:

- use the latest synced `timer` value;
- start a local countdown from the moment the teacher client receives the event;
- refresh that countdown whenever a new real-time event arrives.

This keeps the teacher UI responsive without turning the active sync endpoint into a heartbeat endpoint.

The jump observation views already have `last_sync_received_at` / stale helpers. Reuse that approach in the session tables instead of inventing a different stale-state mechanism.

## 12. Failure Handling Rules

If an active sync request fails:

- keep all pending changes in memory;
- retry on the next scheduled interval;
- do not silently discard unsynced answers.

If the backend rejects a sync because the attempt is no longer in progress, or because the session is no longer active:

- stop the sync loop immediately;
- fetch the latest attempt state if needed;
- redirect or refresh the learner flow according to the existing finished-attempt / expired-session behavior.

If the learner changes a value while a sync is already in flight:

- do not send a second concurrent request;
- keep the new change in the dirty map;
- flush it immediately after the current request finishes.

If the attempt finishes while there are still local dirty answers:

- best-effort sync them first;
- always include the full final `answers` array in the submit request as the authoritative fallback.

## 13. Performance and Simplicity Rules

- Reuse the existing `AttemptUpdated` event instead of creating a parallel event family.
- Keep the current private channel contract unless authorization changes are strictly required.
- Do not add full answer-history storage.
- Do not send sync requests when there are no answer changes.
- Do not broadcast when a sync request produces no effective change.
- Prefer small, local refactors over a broad attempt-system redesign.
- Copy the jump batching implementation. Do not create a shared abstraction in this iteration unless it is already trivial and both call sites stay easy to read.

## 15. Acceptance Criteria

- Starting a session attempt broadcasts a teacher-visible live update immediately.
- During an active session, answer changes are not persisted one by one.
- During an active session, changed answers reach the backend in batches at most once per configured interval when the network is healthy.
- If no answer changes occur, no periodic answer sync request is sent.
- If the same answer changes multiple times inside one interval, only the latest value is persisted.
- Clearing an answer is persisted correctly.
- Numeric answers on questions 25 and 26 (indices 24 and 25) remain valid and are included in batches.
- Guest learners can still start, sync, and submit.
- Teacher active observation updates status, remaining time, and answered count without receiving the full `answers` array.
- Teacher active observation continues to feel live because countdowns are animated locally between sync events.
- `AttemptsTable` can show guests and newly started attempts without a class roster.
- `DivisionAttemptsTable` keeps the class roster visible, including learners who have not started yet.
- Teacher observation does not reorder division roster rows when live updates arrive.
- If live data becomes stale, the UI shows a non-terminal stale indicator instead of incorrectly marking the learner finished.
- Detailed answer chips for finished attempts come from the details/show payload, not from the live event.
- If that fetch is needed and fails, the teacher sees a retry path rather than an empty grid.
- Controlled endings preserve the final learner answer state even when some answers were still unsynced right before submit.
- Browser close and network loss use best-effort final sync behavior and otherwise fall back to the existing timeout or abandon lifecycle.
- Rejoin approval still updates the learner timer through `extra_time` on `AttemptUpdated`.
- Delayed correction, scoring, and results display remain unchanged.
- Jump attempt behavior is unchanged.

## 17. Implementation Guardrails

- Keep the solution narrow and session-specific.
- Reuse existing event and channel names where possible.
- Treat the jump batching code as the reference implementation, not as files to edit.
- Do not redesign unrelated attempt flows.
- Do not add new infrastructure if a focused controller, store, and UI refactor is sufficient.
- If a current API contract is already inconsistent, fix it as part of this feature rather than preserving broken behavior.
- Do not start feature #24 in this change set.

### 17.1 Ask for Clarification Only If One of These Conditions Occurs

- another live consumer of `AttemptUpdated` depends on receiving the full `answers` array and cannot reasonably switch to on-demand fetch;
- changing the payload would break the learner `extra_time` listener and there is no safe summary field to keep;
- the current `AttemptsTable` sort UX is intentionally live-reordering in a way that teachers rely on, and merging in place would alter an approved UX rule;
- guest sync cannot use the current ownership rule because a newly discovered constraint makes unauthenticated batch writes unsafe;
- the batch sync endpoint exposes a constraint not visible in the current code, such as proxy, auth, or browser-unload behavior that makes best-effort final sync materially weaker than assumed here.
