# Fix: Real-Time Notifications for Jump Attempts

## 1. Objective

Reduce backend load generated by active jump attempts while keeping teacher monitoring near real time.

For jump attempts only, replace per-answer persistence and broadcasting with batched synchronization. Teachers must still see meaningful live progress, but the system must stop pushing the full attempt state on every learner input.

## 2. Product Decisions Locked for This Iteration

- This feature applies only to jump attempts, not to Kangourou session attempts.
- Teacher live monitoring during an active jump shows progress only, not the full per-question answer state.
- The live teacher view must update these fields for each learner attempt:
	- attempt status: not started, in progress, finished;
	- remaining time;
	- number of answered questions over total questions;
	- termination reason once the attempt is finished;
	- score once available.
- During an active jump, the teacher UI must not receive the full `question_list` over real-time events.
- The learner client stores only the latest answer per changed question. Intermediate edit history is out of scope.
- The batching interval defaults to 3 seconds and must be defined in one centralized constant so it can be changed later without searching through the codebase.
- Live updates are only sent to teachers already authorized to monitor the jump or the class.
- On browser close, page unload, or network loss, the client makes a best-effort immediate final sync. If the request cannot reach the server, the product falls back to the existing timeout or abandon behavior. Immediate server confirmation cannot be guaranteed for hard disconnects.

## 3. Why This Change Is Needed

The current strategy is too expensive when many learners are active at the same time. Persisting and broadcasting on every learner interaction creates unnecessary write volume and unnecessary event traffic.

This feature changes the contract from:

- every answer change is sent immediately;
- the teacher receives overly detailed live payloads;

to:

- answers are buffered locally and flushed in batches;
- the teacher receives lightweight progress summaries;
- the final state is still persisted immediately when the attempt ends.

## 5. Scope

### In Scope

- batching learner answer persistence for active jump attempts;
- immediate real-time event when a jump attempt starts;
- periodic batched sync while the attempt is active;
- immediate final real-time event when the attempt finishes;
- teacher UI updates based on lightweight progress payloads;
- best-effort final sync on browser close or disconnect scenarios;
- backend and frontend tests for the new contract.

### Out of Scope

- preserving a full history of every intermediate learner answer edit;
- real-time streaming of full per-question answer content during an active jump;
- redesigning jump grading, jump scoring, or jump question selection;
- changes to Kangourou session attempt behavior;
- introducing a new teacher-facing analytics surface.

## 6. User-Visible Behavior

### 6.1 Learner Experience

When a learner starts a jump attempt:

- the attempt is created immediately on the backend;
- the existing jump start behavior remains intact;
- a real-time event is broadcast immediately so authorized teachers can see that the learner has started.

While the learner is answering questions:

- the learner UI updates immediately and optimistically on the client;
- answers are stored locally in memory as pending changes;
- the client does not call the backend for every single answer change;
- every 3 seconds, if there are unsynced changes, the client sends one batched sync request containing the latest value for each changed question;
- if the learner changes the same answer several times inside one interval, only the final value is sent;
- clearing a previously answered question counts as a change and must be sent.

When the learner ends the attempt:

- the system performs a best-effort final sync of any unsent local changes;
- the attempt is then finalized through the existing submit flow;
- a real-time event is broadcast immediately so teachers see the finished state.

Termination paths covered by this feature:

- manual submit;
- manual quit or abandon;
- time expiry;
- blur timeout;
- browser close or page unload, best effort only;
- network disconnect, best effort only;
- teacher or admin forced stop, if such a control already exists in the current jump lifecycle.

### 6.2 Teacher Experience

When a teacher opens the jump observation UI for an active jump:

- the teacher sees the full class roster immediately, including learners who have not started yet;
- the observation UI keeps a stable row order based on the existing roster order and must not reorder rows on each incoming event;
- attempts appear as learners start;
- active attempts update in near real time without requiring a full page refresh;
- the teacher sees progress, not the full answer content, during the active jump.

For active jump monitoring, each learner row must show at least:

- learner identity;
- status;
- remaining time;
- answered count over total questions;
- last update freshness, either directly or through a clear stale-state indicator.

Recommended active-row presentation:

- a compact progress label such as `8 / 15` answers;
- an optional lightweight progress bar if it can be implemented without introducing new complexity;
- a local countdown based on the latest synced timer value;
- a subtle freshness indicator such as `updated a few seconds ago` when the data is getting stale.

The teacher does not need to see the live per-question answer grid while the jump is still in progress.

Teacher observation must support these presentation states:

- `Not started`: learner has no attempt yet;
- `In progress`: learner has an active attempt and recent sync data;
- `Sync delayed`: learner has an active attempt but no refresh has arrived for more than two sync intervals; this is a UI-only state and must not be persisted as a backend attempt status;
- `Finished`: learner attempt is completed.

The UI must not show disruptive feedback for normal live traffic:

- no toast for every incoming event;
- no row flash that makes the table hard to scan;
- only small, unobtrusive row-level updates.

When the attempt is finished:

- the teacher row updates to show the finished state;
- the countdown stops;
- termination is reflected correctly;
- score is shown when available;
- detailed answer review remains accessible through the existing detail flow and must be fetched on demand.

When the teacher opens detailed attempt review:

- the detail modal must fetch the full attempt payload from the existing show endpoint;
- the detail modal must have explicit loading, success, and error states;
- if the fetch fails, the teacher must see a retry path rather than an empty modal.

## 7. Functional Requirements

### 7.1 Start Event

On successful jump attempt creation:

- persist the new attempt as today;
- broadcast `JumpAttemptUpdated` immediately;
- send a lightweight summary payload only, not the full `question_list`.

### 7.2 Active Sync Behavior

During an active jump attempt:

- keep the current attempt state locally in the learner client;
- maintain a dirty map keyed by immutable attempt-local question index;
- sync only when the dirty map is not empty;
- send at most one active sync request at a time for a given attempt;
- if a flush is requested while another flush is in flight, coalesce the new changes and send one additional flush immediately after the current request completes;
- do not send heartbeat writes when nothing changed.

### 7.3 Finalization Behavior

For controlled endings such as submit, timeout, blur timeout, or explicit abandon:

- stop the periodic sync loop;
- attempt a final sync of unsent changes;
- call the submit endpoint with the authoritative final state;
- mark the attempt as finished exactly once;
- broadcast the final summary event immediately.

For uncontrolled endings such as hard disconnect:

- send a best-effort request using browser unload-safe mechanisms;
- if the request does not reach the server, rely on the existing timeout or abandon lifecycle.

### 7.4 Teacher Event Audience

- Continue using the existing private jump channel.
- Only teachers already authorized for that jump or its parent class may receive live updates.
- No learner client should receive another learner's live progress through this feature.

### 7.5 Teacher Monitoring UX Rules

- The teacher observation table must render from the class roster, not from the incoming event stream alone.
- Incoming events enrich existing learner rows rather than creating a separate live-only list.
- A learner with no attempt remains visible as `Not started`.
- A learner row must not disappear just because no new event arrives.
- The UI may derive a `Sync delayed` state when the last event age exceeds two batching intervals, but it must never convert that presentation state into a persisted attempt status.
- Opening detailed review must always trigger a fetch for the authoritative full attempt payload.

## 8. Data Contract

### 8.1 Batched Sync Request

Add a dedicated active-sync endpoint for jump attempts.

Recommended route:

- `PATCH /api/jump-attempts/{jumpAttempt}/sync`

Recommended request body:

```json
{
	"timer": 421,
	"changes": [
		{ "question_index": 2, "answer": "B" },
		{ "question_index": 7, "answer": null }
	]
}
```

Request rules:

- `timer` is optional but should be sent whenever available so teacher progress can stay accurate;
- `changes` is required when a sync is sent;
- each change item must contain:
	- `question_index`: integer, zero-based, must point to a valid entry in `question_list`;
	- `answer`: nullable string, same validation envelope as the current single-answer endpoint.

Response rules:

- a successful active sync may return `204 No Content`;
- the learner client should not depend on the server returning a refreshed full attempt during active sync;
- invalid indices or invalid answer values must return validation errors;
- syncing a finished attempt must be rejected cleanly.

### 8.2 Final Submit Request

Keep the current jump attempt submit endpoint.

The submit request must remain authoritative and must include the final local `question_list` so that unsent local changes are not lost if the last periodic batch has not completed yet.

This means:

- periodic sync sends deltas only;
- final submit sends the full final attempt state.

This is intentionally simpler and safer than trying to guarantee perfect ordering for every network edge case.

## 9. Event Contract

Reuse the existing `JumpAttemptUpdated` event name and channel.

Change the broadcast payload to a lightweight attempt summary.

Recommended payload shape:

```json
{
	"attempt": {
		"id": 123,
		"jump_id": 45,
		"user_id": 9,
		"status": "inProgress",
		"termination": "none",
		"timer": 421,
		"answered_count": 8,
		"total_questions": 15,
		"score": null,
		"updated_at": "2026-07-26T12:34:56Z"
	}
}
```

Payload rules:

- do not broadcast `question_list` for active monitoring;
- include `score` when it exists;
- keep `user_id` so teacher UIs can merge updates into the correct row;
- use `updated_at` as the freshness timestamp unless the implementation introduces a dedicated field for this purpose.

## 10. UI Changes Required

### 10.1 Learner Jump Attempt View

Refactor the learner jump attempt view so that:

- selecting an answer updates local state immediately;
- selecting an answer no longer calls the backend directly for each click;
- the component starts a periodic sync loop while the attempt is in progress;
- the component clears the sync loop on unmount or when the attempt finishes;
- submit, timeout, blur timeout, and unload behavior all pass the authoritative final question state to the submit endpoint.

### 10.2 Teacher Observation Views

The teacher observation UIs currently merge full attempt objects pushed by `JumpAttemptUpdated`.

They must be updated to work with summary payloads instead.

Required changes:

- in active jump observation, replace the live per-question answer chip grid with a compact progress display such as `answered_count / total_questions`;
- keep the roster-based row order stable while live updates arrive;
- render `Not started`, `In progress`, `Sync delayed`, and `Finished` presentation states clearly;
- show last-update freshness when useful, especially for `Sync delayed` rows;
- keep score display for finished states;
- when a teacher opens attempt details, fetch the full attempt on demand using the existing show endpoint instead of assuming the live event payload already contains `question_list`;
- add explicit loading and retry behavior for that detail fetch.

### 10.3 Teacher Observation Interaction Rules

- Clicking a learner row must remain lightweight and predictable; do not force a full observation reload.
- The observation modal must remain usable if one learner detail fetch fails.
- If the active jump expires while the observation modal is open, the teacher view must transition cleanly to the finished state without requiring a manual refresh.
- Live updates must patch the relevant row only; avoid refetching the entire course or division payload on every `JumpAttemptUpdated` event.

### 10.4 Teacher Timer Display

Do not generate extra backend traffic only to animate a countdown.

Instead:

- use the latest synced `timer` value;
- start a local countdown from the moment the teacher client receives the event;
- refresh that countdown whenever a new real-time event arrives.

This keeps the teacher UI responsive without turning the active sync endpoint into a heartbeat endpoint.

## 11. Failure Handling Rules

If an active sync request fails:

- keep all pending changes in memory;
- retry on the next scheduled interval;
- do not silently discard unsynced answers.

If the backend rejects a sync because the attempt is no longer in progress:

- stop the sync loop immediately;
- fetch the latest attempt state if needed;
- redirect or refresh the learner flow according to the existing finished-attempt behavior.

If the learner changes a value while a sync is already in flight:

- do not send a second concurrent request;
- keep the new change in the dirty map;
- flush it immediately after the current request finishes.

If the attempt finishes while there are still local dirty answers:

- best-effort sync them first;
- always include the full final `question_list` in the submit request as the authoritative fallback.

## 12. Performance and Simplicity Rules

- Reuse the existing `JumpAttemptUpdated` event instead of creating a parallel event family.
- Keep the current private channel contract unless authorization changes are strictly required.
- Do not add full answer-history storage.
- Do not send sync requests when there are no answer changes.
- Do not broadcast when a sync request produces no effective change.
- Prefer small, local refactors over a broad attempt-system redesign.

## 14. Acceptance Criteria

- Starting a jump attempt broadcasts a teacher-visible live update immediately.
- During an active jump, answer changes are not persisted one by one.
- During an active jump, changed answers reach the backend in batches at most once per configured interval when the network is healthy.
- If no answer changes occur, no periodic answer sync request is sent.
- If the same answer changes multiple times inside one interval, only the latest value is persisted.
- Clearing an answer is persisted correctly.
- Teacher active observation updates status, remaining time, and answered count without receiving the full `question_list`.
- Teacher active observation continues to feel live because countdowns are animated locally between sync events.
- Teacher observation keeps the class roster visible, including learners who have not started yet.
- Teacher observation does not reorder rows when live updates arrive.
- If live data becomes stale, the UI shows a non-terminal stale indicator instead of incorrectly marking the learner finished.
- Detailed attempt review fetches the full attempt on demand and exposes a loading and retry state.
- Controlled endings preserve the final learner answer state even when some answers were still unsynced right before submit.
- Browser close and network loss use best-effort final sync behavior and otherwise fall back to the existing timeout or abandon lifecycle.
- Only authorized teachers receive live jump attempt updates.
- Jump grading, score calculation, and results display remain unchanged.

## 16. Implementation Guardrails

- Keep the solution narrow and jump-specific.
- Reuse existing event and channel names where possible.
- Do not redesign unrelated attempt flows.
- Do not add new infrastructure if a focused controller, store, and UI refactor is sufficient.
- If a current API contract is already inconsistent, fix it as part of this feature rather than preserving broken behavior.

### 16.1 Ask for Clarification Only If One of These Conditions Occurs

- another live consumer of `JumpAttemptUpdated` depends on receiving the full `question_list` and cannot reasonably switch to on-demand fetch;
- the codebase contains an existing teacher or admin forced-stop jump flow whose finish semantics conflict with this document;
- the current teacher observation rows are intentionally sorted by something other than class-roster order and changing that would alter an approved UX rule;
- the current timer semantics in the learner and teacher views are inconsistent enough that `timer` cannot safely act as the shared progress signal;
- the batch sync endpoint exposes a constraint not visible in the current code, such as proxy, auth, or browser-unload behavior that makes best-effort final sync materially weaker than assumed here.

## 17. Definition of Done

This feature is complete when:

- the learner jump experience remains responsive;
- teacher jump monitoring remains useful and near real time;
- backend write and broadcast volume for active jumps is materially reduced;
- the implementation is covered by focused automated tests;
- the jump attempt live-update contract is simple enough for future maintenance.
